# Project pack and coordination protocol

Read this only after product direction is approved or when resuming an existing initiative created by this Skill.

## 1. Workspace selection

Keep three locations distinct:

1. **Skill home:** the personal installation directory; contains only reusable instructions.
2. **Initiative workspace:** contains product-governance files for this idea.
3. **Target product/code repository:** receives implementation only after the placement gate.

Use a workspace explicitly supplied or approved by the user. If none exists, recommend a neutral initiative directory and show its exact absolute path before creating it. A familiar repository, the current directory, a memory, or a prior example is not implicit authorization. Never enumerate outside the roots authorized in the current request.

## 2. Minimal governance pack

```text
<initiative-workspace>/
├── PROJECT-COMPASS.md
├── PRODUCT-ROADMAP.md
├── PLAN.md
├── REGISTRY.yaml
├── DECISIONS.md
├── PROGRESS.md
├── ACCEPTANCE.md
├── contracts/
└── evidence/          # create only when research produces source artifacts
```

Do not create parallel files when the selected workspace already has an equivalent governed format. Map the required fields to existing files and record that mapping in `REGISTRY.yaml`.

### `PROJECT-COMPASS.md` — why and boundaries

Required fields:

- `initiative_id`, title, owner, approved version, current stage
- raw idea and clarified decision question
- target users and existing workflow/problem
- desired outcome and why it matters
- facts, assumptions, unknowns, counter-evidence
- non-goals and net-burden/safety/privacy boundaries
- success evidence, failure/stop thresholds, reopening conditions
- placement status: `unassigned`, `research_only`, `existing_product`, `neutral_incubation`, or `new_project`

Only the coordinator may edit it. Product-level changes require a new recorded decision and user approval.

### `PRODUCT-ROADMAP.md` — conditional horizons

Use this shape for each horizon:

| Horizon | Outcome | User/workflow | Hypothesis | Evidence gate | Deliverables | Stop/pivot condition | Status |
|---|---|---|---|---|---|---|---|
| Near | Next proof-producing outcome | ... | ... | ... | ... | ... | approved/current |
| Mid | Repeatability, integration, or operating proof | ... | ... | Requires near evidence | ... | ... | conditional |
| Long | Scale or broader product option | ... | ... | Requires mid evidence | ... | ... | option |

Use dates only when resourcing and dependencies support them. Otherwise use outcome gates; do not invent precision.

### `PLAN.md` — current phase only

Each active task includes:

- task ID and title
- `serves_goal` and approved roadmap phase
- owner/task/thread
- inputs and dependencies
- allowed files or external systems
- deliverable and acceptance evidence
- status, blocker, and next action

Tasks for unapproved mid/long horizons do not belong here.

### `REGISTRY.yaml` — runtime identities

Record stable mappings, not narrative:

```yaml
initiative_id: "..."
workspace: "absolute path"
target_product: null
target_repository: null
placement_decision: "decision id"
contract:
  path: "contracts/current.md"
  version: "..."
goal:
  id: null
  status: "not_created"
threads: []
taskboard:
  system: null
  project_id: null
  last_readback: null
```

Update goal/task/thread/board IDs only from live tool results. Use `not_created` before a contract is ready, `proposed_not_started` only when a contract is ready but live goal execution is unavailable, `active` only after creation/readback, and then the runtime's verified terminal status. A failed call leaves the prior status unchanged and records a blocker in `PROGRESS.md`.

### Single-writer ownership

| Path | Only writer | Other roles |
|---|---|---|
| `PROJECT-COMPASS.md`, `PRODUCT-ROADMAP.md`, `PLAN.md`, `REGISTRY.yaml`, `DECISIONS.md`, `PROGRESS.md` | coordinator | submit handoffs or decision requests |
| `contracts/` | coordinator, after `leader` drafts and the user approves | leader proposes; executor reads |
| `ACCEPTANCE.md` | independent reviewer | coordinator and executor read; user acceptance is recorded separately in `DECISIONS.md` |
| `evidence/<task-id>/` | the one task assigned that directory | coordinator reads and indexes |

Implementers never directly edit central governance files. One task owns each evidence/artifact path; no two tasks share a write target.

### `DECISIONS.md` — append-only authority

Each decision records ID, date, question, options, facts, inference, risks, choice, decider, affected files/tasks, and reopening trigger. Child tasks submit decision requests; they do not edit this file.

### `PROGRESS.md` — append-only resume log

At each checkpoint, the coordinator records stage and decision, files changed, live goal/task IDs, completed result, raw verification reference, remaining work, blockers, next owner/action, unresolved risks, and waiting state. Activity without evidence is not progress toward acceptance.

### `ACCEPTANCE.md` — frozen criteria and review

The independent reviewer alone records contract version, visible checks, reviewer identity, independence statement, evidence, spot-check results, verdict, and remaining risks. Concealed checks stay in the reviewer context until run; record their result afterward. The coordinator records later user acceptance as a separate decision so reviewer evidence is not rewritten.

## 3. Topics, child tasks, and models

Use a coordinator-and-spokes topology. When the user has authorized separate conversations and the host exposes task/thread tools, independent themes must use user-visible Codex tasks so the user can open, steer, or stop them. Record each task's ID, title, role, parent, model class, reasoning level, status, and handoff path in `REGISTRY.yaml`. If visible task tools are unavailable, use internal subagents only as an explicitly labeled fallback; never claim that an internal subagent is a user-visible task.

The coordinator owns central governance and broadcasts approved decisions to every affected task. Visible tasks submit evidence, blockers, and decision requests back to the coordinator; they do not negotiate or redefine the goal among themselves. Create them only when work is independent and user authorization exists.

Every child handoff contains:

- goal and approved phase served
- exact question and non-goals
- allowed reads/writes
- expected evidence/artifact
- decision requests and blockers
- final status and next recommended action

Select from models currently available at dispatch time:

- bounded scanning/extraction: efficient model, low or medium reasoning
- product synthesis, premise audit, or independent verification: strongest suitable model, high reasoning
- implementation: suitable coding model, medium by default; raise only for genuinely complex architecture or debugging

Do not hard-code model names. One writer owns each shared file. The user may inspect, redirect, or stop a visible task, but product-level changes still pass through the coordinator, `DECISIONS.md`, and the required approval gate.

## 4. Project and code placement gate

Inspect only candidate products and repositories named in the current request or located under an explicitly approved current-run search root. Re-verify any memory-derived clue before using it. Assess user overlap, workflow fit, capability reuse, architecture, ownership, permissions, data/privacy boundaries, operational cost, and roadmap conflict. Record alternatives including no build.

After approval, `PLAN.md` must name:

- target repository and isolated work location
- existing repository conventions and governing instructions
- exact source, test, schema, documentation, and generated-artifact paths
- which files are created, modified, generated, or forbidden
- validation commands verified in the actual environment
- rollback/integration path

No code layout is invented before this inspection. A new repository or project requires explicit approval.

## 5. Taskboard ownership

Taskboard use is optional.

- Without a confirmed board, `PLAN.md` owns task status.
- With a confirmed board, files own goal/scope/acceptance while the board owns assignee and operational status.
- After every create, move, or comment, read back the task ID, version, and status into `REGISTRY.yaml`/`PROGRESS.md`.
- A board item marked done without acceptance evidence is operationally closed but not product-accepted; record the mismatch and stop reconciliation.

## 6. Drift routing

| Change or failure | Route |
|---|---|
| Value, target user, problem, product shape, placement, roadmap gate | Return to `superpowers:brainstorming` and user approval |
| Current-phase scope, allowed files, acceptance, or stop condition | Pause goal; return to `leader` and approve a revised contract |
| Implementation method within frozen boundaries | Executor may choose; explain in progress log |
| Failed verification within valid premise | `leader` creates a bounded correction contract |
| Evidence disproves premise or net value | Return to brainstorming for pivot/hold/stop |
